# /analyze-bug: 버그 분석 문서 생성

이슈 번호 또는 beads ID, 혹은 버그 설명을 받아서 분석 문서를 생성한다.

입력: $ARGUMENTS (GitHub 이슈 번호, beads ID, 또는 버그 설명)

## 실행 절차

### 1단계: 이슈 정보 수집

- GitHub 이슈 번호가 주어지면 `gh issue view <번호>` 로 상세 내용 조회
- beads ID가 주어지면 `bd show <id>` 로 상세 내용 조회
- 텍스트 설명이 주어지면 그대로 사용

### 2단계: 코드 탐색 및 원인 분석

- 이슈에 언급된 파일들을 모두 읽는다
- 관련 코드 흐름을 추적한다 (호출자 → 함수 → 하위 레이어)
- 검증 레이어별로 문제 지점을 식별한다 (프론트엔드, 스키마, 서버, DB)

### 3단계: 문서 작성

`docs/diary/{오늘날짜}_{slug}.md` 파일에 아래 구조로 작성한다.

```markdown
# [{우선순위}] {버그 제목} ({이슈 참조})

## 버그 요약
한 줄 요약.

## 영향 범위
- **사용자 영향**: 사용자가 겪는 증상
- **데이터 영향**: DB 정합성 문제 여부
- **보안 영향**: 보안 리스크 여부

## 원인 분석
레이어별 (프론트엔드/스키마/서버/DB) 원인을 코드 참조와 함께 설명.
각 레이어에서 검증이 있는 부분(✅)과 누락된 부분(❌)을 명확히 구분.

## 해결 방안
Fix 단위로 분리하여 작성. 각 Fix에:
- **파일**: 수정 대상 파일 경로
- **위치**: 수정 위치 (함수명, 라인)
- **변경 내용**: 코드 diff 또는 코드 블록

## 수정 순서
번호 매긴 실행 순서.

## 테스트 케이스
카테고리별 표로 정리:

| # | 조건 | 조작 | 기대 결과 |
|---|---|---|---|
| {카테고리}-{번호} | 사전 상태 | 사용자 행동 | 예상 결과 |

카테고리 분류 기준:
- **핵심 수정**: 이번 버그가 직접 재현되는 케이스 (반드시 포함)
- **회귀 방지**: 기존 정상 동작이 깨지지 않는지 확인
- **경계값**: 최소/최대/빈값/특수문자 등 edge case
- **서버 검증**: API 직접 호출로 우회 시도
- **데이터 정합성**: 저장 후 재로드, 기존 비정합 데이터 처리

## 관련 파일
수정 대상 파일과 변경 내용 요약 표.
```

### 4단계: 확인

- 문서 경로를 사용자에게 알려준다
- 핵심 원인과 수정 포인트를 간략히 요약한다

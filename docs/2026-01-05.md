## Webhook Formatter 코드 리뷰 (PR #47 관련)

### 1. TYPE_COLORS 상수 선언

`discord.ts`의 TYPE_COLORS 변수에서 `as const`와 타입 선언의 관계를 검토함.

**현재 코드:**
```typescript
const TYPE_COLORS: Record<string, number> = {
  BUG: 0xef4444,
  FEATURE: 0x8b5cf6,
  INQUIRY: 0x3b82f6,
} as const;
```

**문제:** `Record<string, number>` 타입 선언이 `as const`의 narrowing 효과를 덮어씀.

**`as const` vs `satisfies` 차이:**
- `as const`: 값을 정확한 리터럴 타입으로 좁힘
- `satisfies`: 타입 체크만 하고 추론된 타입은 유지
- `as const satisfies`: 둘의 장점 결합

**결론:** `feedback.type`이 `string`이고 동적 키로 접근하므로 `Record<string, number>`가 적절. `as const`는 효과 없으니 제거 권장.

### 2. discordFormatter 함수 길이

`format` 함수가 약 30줄이라 20줄 가이드라인 위반 여부 검토.

**분석:**
- 실제 로직은 3줄, 나머지는 객체 구조 정의
- 20줄 규칙은 복잡한 로직을 쪼개라는 취지
- 데이터 구조를 쪼개면 오히려 가독성 저하

**결론:** 현재 코드 유지. 과도한 분리는 오버엔지니어링.

---

### 3. getFormatter 스푸핑 문제

`webhookUrl.includes(pattern)` 방식의 URL 매칭에서 스푸핑 가능성 제기됨.

**문제 예시:**
```
https://evil.com/hooks.slack.com/fake → Slack으로 잘못 인식
```

**검토 결과:**
- Webhook URL은 관리자만 설정 가능 (공격자 입력 불가)
- 잘못된 formatter 선택 시 전송 실패할 뿐, 보안 취약점 아님
- hostname 파싱으로 방어 가능하나 이 맥락에서는 오버엔지니어링

**결론:** 현재 코드로 충분. 필요시 `new URL(url).hostname.endsWith(pattern)` 방식으로 개선 가능.

## Webhook 타입 Zod 스키마 통합 리팩토링

### 문제

`apps/web/src/lib/webhook/types.ts`에서 `FeedbackData`, `ProjectData`, `OrganizationData`를 수동으로 정의하고 있었음.

```typescript
// 기존 코드 - 중복 정의, 느슨한 타입
export interface FeedbackData {
  type: string;  // ❌ 느슨한 string
  // ...
}
```

`@sori/database`에 이미 Zod 스키마 기반 타입이 존재:
- `FeedbackType = "BUG" | "INQUIRY" | "FEATURE"`
- `Feedback`, `Project`, `Organization` 타입

### 해결

1. **types.ts**: `@sori/database`에서 타입 import, `Pick<>` 유틸리티 사용
   ```typescript
   import type { FeedbackType, Project, Organization } from "@sori/database";

   export interface FeedbackData {
     type: FeedbackType;  // ✅ 엄격한 union 타입
     // ...
   }

   export type ProjectData = Pick<Project, "id" | "name">;
   export type OrganizationData = Pick<Organization, "id" | "name">;
   ```

2. **utils.ts**: switch문 → `Record<FeedbackType, TypeInfo>` 맵으로 변경
   ```typescript
   const TYPE_INFO_MAP: Record<FeedbackType, TypeInfo> = {
     BUG: { emoji: "🐛", label: "버그 리포트" },
     FEATURE: { emoji: "💡", label: "기능 요청" },
     INQUIRY: { emoji: "❓", label: "문의" },
   };
   ```

3. **discord.ts**: `TYPE_COLORS` 타입을 `Record<FeedbackType, number>`로 변경, 불필요한 fallback 제거

4. **organization.ts, webhook.ts**: 테스트 데이터에 `as const` 추가로 리터럴 타입 추론

### 효과

- 새 FeedbackType 추가 시 TypeScript가 누락된 케이스를 **컴파일 타임에 감지**
- 중복 타입 정의 제거로 **유지보수성 향상**
- CLAUDE.md 가이드라인 준수: "Zod 스키마로 타입 정의 + z.infer<>로 타입 추론"
